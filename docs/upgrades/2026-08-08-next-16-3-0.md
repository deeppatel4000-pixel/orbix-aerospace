## Phase 3 — compatibility fixes (three, each tied to a specific Next 16 change)

1. **`eslint.config.mjs` — flat-config migration.** The previous `FlatCompat` + `compat.extends("next/...")` shim hard-crashed under `eslint-config-next@16`:
   `Converting circular structure to JSON ... property 'react' closes the circle`. The v16 configs are self-referential and the eslintrc compatibility layer serialises them for schema validation. Migrated to the documented native subpath imports (`eslint-config-next/core-web-vitals`, `eslint-config-next/typescript`). Rule coverage is unchanged — same two config sets, same order, `eslint-config-prettier` still applied last.

2. **`src/app/layout.tsx` — `data-scroll-behavior="smooth"` on `<html>`.** Next 16 no longer force-normalises `scroll-behavior` during route transitions unless this attribute is present. ORBIX sets `scroll-behavior: smooth` globally in `orbix-foundations.css`, so without it every navigation would animate-scroll instead of snapping. Reduced-motion behaviour is unaffected.

3. **`next.config.ts` — `images.localPatterns`.** **This one was missed by the pre-upgrade audit and was only caught by running the build.** Next 16 requires local `next/image` sources carrying a query string to be explicitly allowed. `site-logo.tsx` requests `/brand/orbix-wordmark-transparent.png?surface=site-chrome`, which failed prerendering of `/aircraft` and `/rockets` with `next-image-unconfigured-localpatterns`. Two patterns are declared, because declaring `localPatterns` at all turns it into an allowlist: `{ pathname: "/**", search: "" }` for every normal asset, plus the one surface marker.

Additionally, Next auto-rewrote `tsconfig.json`: `jsx: "preserve"` → `"react-jsx"` (mandatory in 16) and added `.next/dev/types/**/*.ts` to `include`. Verified this does **not** churn against Prettier — Next only rewrites when it needs to change something, and `format:check` passes after a single reformat.

## Phase 4 — the lint findings, and why they were suppressed rather than refactored

`npm run lint` reported 4 `react-hooks/set-state-in-effect` errors. Investigated rather than reflex-fixed. Findings:

- The rule arrived via **`eslint-plugin-react-hooks` 5.2.0 → 7.1.1**, a transitive major that rode along with `eslint-config-next@16`. It is a React Compiler rule, `error` by default in the recommended preset. It is not a Next-specific decision.
- All four flagged files are **byte-identical to the pre-upgrade baseline** (verified with `git diff` against the rollback tag). These are already-shipped, already-tested patterns newly reclassified — not upgrade regressions.
- Two sites (`laboratory-shell.tsx` reading `window.location.hash`, `scenario-library.tsx` reading `localStorage`) are the textbook SSR-safe "synchronise with an external system" pattern. React's own issue tracker (facebook/react#34743) documents that this rule currently has no accepted alternative for it.
- **No hydration risk** at any of the four: each initialises state from values identical on server and client, so the first client render always matches the SSR output.

Targeted `eslint-disable-next-line` with a per-site justification was chosen over refactoring, because refactoring load-bearing components (the Laboratory's hash routing, the scenario library's persistence) is exactly what a stability-focused upgrade should not do. The rule stays enabled repo-wide, so new violations are still caught.

**Follow-up worth doing separately** (deliberately out of scope): `mission-profile-analyzer.tsx`'s effect exists only because one of its three call sites (`mission-scenario-builder.tsx:728`) does not remount via `key` as the other two do. Unifying that would let the effect be deleted outright.
